# 6. 后端模式菜单树构建引用错误 — 双层嵌套侧边栏问题排查

> 日期：2026-08-14 ｜ 关联提交：`cd53273` fix: 后端模式菜单树构建引用错误——双层嵌套侧边栏与子页面失联触发背景：`VITE_ACCESS_MODE=backend` 切换 + iam_menu 清空重建（55 节点新树）后的浏览器验收

## 1. 现象（用户验收反馈）

后端控制模式下登录后，布局严重异常：

1. **左侧侧边栏双层嵌套**——侧边栏区域出现两列菜单，内容区表头（折叠/刷新/网格按钮）与标签页栏整体重复出现一段；
2. **侧边栏无法展开/收缩**；
3. 侧边栏只显示 5 个顶级目录（仪表盘/只读镜像/系统管理/结果页面/异常页面）， **没有任何子菜单**。

## 2. 排查路径

1. **读管线代码**：`src/router/core/MenuProcessor.ts`（菜单树转换）→ `RouteTransformer.ts`（路由转换）→ `RouteRegistry.ts`（注册）→ `guards/beforeEach.ts`（调用链），确认后端模式数据流： `get_user_menu()` → 两遍建树 → `convertMenuTreeToRoutes` → `normalizeMenuPaths` → 注册；
2. **实测库内数据**：WSL 中 `SET request.jwt.claims` 模拟超管调用 `api_v1_public.get_user_menu()`，确认真实数据形态（55 行：5 目录 + 22 菜单 + 27 按钮 + 1 隐藏页）；
3. **离线模拟全管线**：用库内真实 JSON 在本地脚本中完整重放 `convert → filterEmptyMenus → normalizeMenuPaths → RouteTransformer.transform`，打印最终路由树定位异常（该手法可复用于任何菜单/路由问题排查）。

## 3. 根因

`MenuProcessor.processBackendMenu` 的两遍树构建存在**引用不一致**：

```ts
// 第一遍：nodeMap 存副本
routeItems.forEach((item) => nodeMap.set(item.id, { ...item }))

// 第二遍（原代码）：children 挂到副本上，roots 推的却是原对象
routeItems.forEach((item) => {
  if (item.parent_id && nodeMap.has(item.parent_id)) {
    const parent = nodeMap.get(item.parent_id)! // ← 副本
    parent.children.push(item) // ← 原对象挂入副本
  } else {
    roots.push(item) // ← 原对象，永远没有 children
  }
})
```

**父节点 `children` 挂载在 nodeMap 副本上，而 `roots` 数组推入的是 `routeItems` 原对象**——根节点永远拿不到已挂载的子节点。由此连锁触发：

1. 5 个顶级目录全部以「无 children」形态进入 `RouteTransformer.transform`；
2. 无子路由的顶层路由命中 `handleFirstLevelRoute`（depth 0 且无 children 的分支）：父路由加载 Layout，子路由（目录自身，component='/index/index'）**再次加载 Layout** → Layout 嵌套 Layout = 双层侧边栏/表头，折叠按钮形同失效；
3. 22 个菜单页面只挂在被丢弃的 nodeMap 副本上，**从未进入路由树、从未注册**，直接导航子页面路径会 404。

## 4. 为什么此前没暴露

该代码自 `650f6b7` 起已存在，但旧库内菜单数据形态（顶层多为无目录的扁平菜单行）下，顶层叶子走 `handleFirstLevelRoute` 时子组件是真实页面而非 Layout，布局正常；2026-08-14 菜单清空重建后，顶层目录行 `component='/index/index'`（Layout 别名）成为标准形态，引用了该分支才首次暴露。**数据形态变化可以激活潜伏的管线缺陷**，菜单种子变更后必须全链路验收。

## 5. 修复

`src/router/core/MenuProcessor.ts`（约 L114-L127）——挂载与 roots 统一取 nodeMap 副本：

```ts
// 挂载与 roots 必须统一取 nodeMap 副本：此前父节点 children 挂的是副本、
// roots 推的是原对象——根节点永远拿不到已挂载的子节点，目录被当成无子路由
const roots = []
nodeMap.forEach((node) => {
  if (node.parent_id && nodeMap.has(node.parent_id)) {
    const parent = nodeMap.get(node.parent_id)!
    parent.children = parent.children || []
    parent.children.push(node)
  } else {
    roots.push(node)
  }
})
```

与既有同类写法对齐（`views/system/dept/index.vue`、`position/index.vue`、 `role/modules/role-permission-dialog.vue`、`menu/index.vue` 资源树均正确使用副本）。

## 7. 经验沉淀

1. **两遍树构建铁律**：nodeMap 副本、父节点 children、roots 三处必须引用同一份对象；排查此类问题时优先对比同类实现（dept/position/role/menu 页均为正确范式）。
2. **症状指纹**：「侧边栏只剩 N 个顶级目录（无子菜单）+ 内容区重复表头/标签页」= 顶级路由被 `handleFirstLevelRoute` 误判为叶子 → Layout 包裹 Layout，可直奔 MenuProcessor 两遍建树段。
3. **`handleFirstLevelRoute` 语义**：仅当 depth=0 且**无 children** 才用 Layout 包裹；后端模式目录行 component 必须是 '/index/index'（Layout 别名），一旦目录丢失 children，该分支会把 Layout 当子页面再包一层。
4. **离线模拟管线是可复用排查工具**：库内 `get_user_menu()` JSON + 前端管线（convert → filterEmptyMenus → normalizeMenuPaths → RouteTransformer）脚本重放，秒级输出最终路由树，免登录免浏览器即可断言「有无嵌套 Layout/页面是否全量注册」。
5. **菜单种子变更需全链路验收**：数据形态（目录行 Layout 别名、绝对路径子路由等）是管线的隐性输入契约，重建菜单后除了侧边栏可见性，还要验证子页面导航与折叠交互。
